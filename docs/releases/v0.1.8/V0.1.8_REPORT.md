# TenzorPipe 0.1.8 — Chunked N-Worker Video Decode

**Status:** implemented, byte-identical to 0.1.6 on every tested case, **not yet benchmarked on the EPYC host.** All numbers below come from a 2-core cloud sandbox and the logs in `evidence/v0.1.8-*`.

## 1. What changed

| Area | Change |
|---|---|
| `src/video_parallel.rs` (new) | IDR chunk planner, epoch pre-assignment, window-bounded ordered worker pool, per-chunk decode |
| `src/main.rs` | `--video-workers`, `--chunk-target-ms`, `--video-buffer-mib`; dispatch to parallel path when N > 1 |
| `src/video.rs` | Helpers made `pub(crate)` only. **The single-decoder code is unchanged.** |
| `src/metrics.rs` | New stages `video_window_wait`, `video_reorder_wait` |
| Default | `--video-workers 1` = exact 0.1.6 path |

### Design

1. **Metadata pre-pass.** Reads every sample's timing and IDR flag from the container. It does not read picture data.
2. **Valid cut points.** A split is allowed at sample *k* only when all three hold:
   - the sample is marked sync;
   - its first VCL NAL is type 5 (IDR);
   - every earlier sample presents before every later one.

   Open-GOP I-frames are rejected. A test clip confirms this: `gen-open-gop.mp4` falls back to the single decoder.
3. **Epoch selection up front.** The v0.1.6 `epoch_end` midpoint and tie rules run once over the sorted presentation times. Each chunk then knows exactly which pictures to convert. A chunk edge can't change which frame an epoch gets.
4. **Workers.** Each chunk gets a fresh OpenH264 decoder and a flush at its end. The v0.1.6 validations run per chunk: parameter-set check, reorder ≤ 34, resolution, PTS agreement, and picture count.
5. **Ordered window.** A worker may claim chunk *c* only while `c < next_emit + window`. Finished chunks wait in a `BTreeMap` and are forwarded in order into the existing video channel. The collector and audio worker are untouched.
6. **Failure handling.** The first real error wins, the cancel flag is set, the condvar wakes everyone, and all scoped threads join. Worker panics become errors.
7. **Fallback reasons, always logged:** fewer than 2 chunks, duplicate PTS, or a budget too small for two in-flight chunks.

### 2.1 Identity matrix scope
- **19 files:** all existing video, audio, and failure fixtures, plus `long-30.mp4` (15 chunks), `gen-720-g45.mp4`, `gen-baseline-g12.mp4` and `gen-open-gop.mp4`.
- **4 settings:** 224/0.5 s; 160/0.33 s/batch 2; 336/1.0 s; 224/0.05 s in sequential execution.
- **Worker counts:** N = 1, 2, 4, 8. Each N > 1 also ran with `--chunk-target-ms 250` and with `--video-buffer-mib 1` (forces fallback).
- The 330-second clip was also identical across 0.1.6 and N = 1, 2, 3 and 4 in every benchmark run.
- Output files are compared byte for byte. The only permitted difference is the embedded `tenzor_version` string, which is the same length and appears twice.

### 2.2 New unit tests
- `chunked_selection_matches_streaming_selection`: the pre-computed selection equals the v0.1.6 streaming loop for windows of 50, 330, 500 and 1000 ms.
- `chunks_cut_only_at_idr_with_clean_presentation_boundary`: covers open-GOP-like overlap and sync samples that are not IDR.
- `first_vcl_idr_detection`
- `ordered_map_preserves_order_and_bounds_window`: later chunks finish first, output stays ordered, and in-flight work stays ≤ N.
- `ordered_map_failures_and_panics_do_not_deadlock`: injects failures in the first, middle and last chunk, a panic, and an emitter (writer) failure.
- `external_cancellation_stops_workers`

### 2.3 Known behaviour differences
- **Which error is reported first.** On a file corrupted in both tracks, the parallel path can report the video error where 0.1.6 reported the AAC error, because video reaches the damage sooner. Both versions fail.
- **Timing of timestamp errors.** A presentation-order violation is now found in the pre-pass (and triggers fallback) instead of partway through decoding.

## 3. Performance (2-core sandbox — not the target host)

- **Host:** Intel Xeon @ 2.10 GHz, 2 vCPUs.
- **Test:** `long-330.mp4` (640×360, 30 fps, 2 s GOP), 224 px, 0.5 s window, batch 32.
- **Method:** 1 warm-up then 5 runs per variant. RSS is the sampled `VmHWM`.
- **Build:** Rust 1.95.0. The pinned 1.98.1 toolchain could not be downloaded here.

| Variant | Median wall | Range | CPU | Peak RSS |
|---|---:|---:|---:|---:|
| 0.1.6 | 11.35 s | 11.28–11.51 | 155% | 61.7 MiB |
| 0.1.8 N=1 | 11.27 s | 11.07–11.53 | 156% | 61.4 MiB |
| **0.1.8 N=2** | **9.49 s** | 9.48–9.65 | 187% | 82.8 MiB |
| 0.1.8 N=3 | 9.75 s | 9.55–9.81 | 185% | 97.6 MiB |
| 0.1.8 N=4 | 9.75 s | 9.60–9.91 | 186% | 115.2 MiB |

**Reading it:**
- **The stall is gone.** Workers no longer sit idle: CPU rises to the 2-core ceiling, and N=2 cuts median wall time by 16%.
- **Why it stops at N=2 here.** There are only 2 cores for video workers, the audio worker and the collector. Extra workers just compete for CPU. This shows up as `video_decode` summed across workers growing from 10.5 s to 19.4 s, and `video_window_wait` growing to 16 s at N=4.
- **Memory.** RSS grows about 15–20 MiB per extra worker (decoder state, per-thread allocator arena, buffered chunk tensors). Resident memory is no longer a flat ~60 MiB when N > 1. Plan N against memory as well as cores.
- **Chunk size barely matters** at 2 or 8 seconds (165 vs 42 chunks at N=2: 9.5 s vs 9.4 s). A 30 s target falls back, because 60 buffered pictures × window 3 exceeds 64 MiB.

## 4. To run on the EPYC host

```sh
cargo build --release --locked            # pinned 1.98.1 toolchain
cargo test --locked --all-targets
scripts/gen_v018_fixtures.sh              # long-330, long-30, multi-IDR and open-GOP clips
export TENZOR_OLD_BINARY=/path/to/v0.1.6/tenzor
python3 scripts/test_chunked_identity.py baseline720.mp4,high-bframes.mp4,long-30.mp4,gen-720-g45.mp4,gen-baseline-g12.mp4,gen-open-gop.mp4,selection-vfr.mp4,corrupt-nal.mp4
python3 scripts/fuzz_chunked_corruption.py
# edit the variants list to add N=8/16 on the 80-core host
RUNS=5 python3 scripts/benchmark_video_workers.py
```

**Promotion rule** (unchanged from the directive): change the default only if identity passes on that host and the median wall time beats run-to-run spread. The new default is the smallest N within 5% of the best median. Check RSS at that N too.

## 5. What this does not cover yet
- **Not measured on the EPYC host.** Scaling beyond 2 cores is unmeasured.
- **Audio is next.** On 2 cores, `audio_source` (AAC decode, ~4.3 s) is larger than `audio_resample` (~2.0 s). If audio becomes the critical path, profile AAC decode before hand-vectorizing the resampler.
- **No sanitizer run.** ASan/Valgrind soak was not run.
- **v0.1.7 was not profiled.** Its source wasn't available, so its stall diagnosis is inferred from its design, not measured.
- **Toolchain.** The zip is source only. It was built and tested with Rust 1.95.0, not the pinned 1.98.1. The v0.1.6 release metadata moved to `docs/releases/v0.1.6-metadata/`, and the v0.1.6 binary was removed from `bin/`.
