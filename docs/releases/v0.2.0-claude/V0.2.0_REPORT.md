# TenzorPipe 0.2.0 — Audio Path Speedup

**Status:** implemented and verified. Output is **byte-identical to v0.1.9** everywhere it was tested; the only difference is the embedded version string. All measurements come from a 2-core cloud sandbox, so **the EPYC host still needs a re-run** (commands in §5).

## 1. Result

Median of 5 runs after a warm-up, alternating order. Input is the 330-second clip (640×360 H.264 plus 48 kHz stereo AAC), 224 px, 0.5 s window, batch 32.

| Workload | v0.1.9 bundled binary | v0.1.9 same toolchain | **v0.2.0** | Change (same toolchain) |
|---|---:|---:|---:|---:|
| Audio-only | 6.941 s | 6.293 s | **1.684 s** | **−73%** (3.7× faster) |
| Audio-only, `--no-audio-decode-thread` | — | 6.293 s | 2.240 s | −64% (single thread) |
| Full A/V, `--video-workers 2` | — | 9.501 s | **7.209 s** | −24% |
| Full A/V, `--video-workers 1` | — | 11.314 s | 11.195 s | −1% (the single video decoder sets the time) |

| Audio stage (audio-only) | v0.1.9 | v0.2.0 |
|---|---:|---:|
| `audio_source` (AAC decode) | 4.06 s | 1.54 s (on its own thread) |
| `audio_resample` | 1.91 s | 0.45 s |
| `audio_mel` | 0.30 s | 0.30 s |
| Peak RSS | 10.4 MiB | 10.7 MiB |

- **Full-pipeline memory:** peak RSS is unchanged or lower (N2: 81.0 → 77.2 MiB).
- **Output hashes:** every run of each variant produced the same output file.
- **Critical path:** on this 2-core machine, audio-only now takes 1.7 s against about 7 s for the full pipeline, so video decoding is what sets total wall time.
- **Earlier EPYC numbers:** v0.1.9 measured video-only N2 at 4.726 s and audio-only at 6.585 s there. Audio should now finish well before video on that host too, but that needs to be measured there.

## 2. What changed and why

Instruction-level profiling of v0.1.9 (callgrind, 20 s AAC clip) showed:

| Hotspot (v0.1.9) | Share | Fix | Output effect |
|---|---:|---|---|
| Huffman decode: linear scan of the whole codebook for every bit | ~39% | 11-bit lookup table per codebook; long, invalid or truncated codes use the original scan | Identical symbols, bit positions and errors |
| Resampler `VecDeque` access with per-tap checks | ~25% | Contiguous PCM buffer; same-order dot product when all 129 taps are present; release consumed samples in 32,768-sample blocks | Same products, same accumulation order → identical |
| IMDCT: new 8192-point buffer and FFT scratch allocated and zeroed on every call | ~22% | Reuse per-thread buffers | Same FFT plan and inputs → identical |
| `powf` in dequantization and scalefactor gain | ~6% | Tables filled with the identical expressions | Tested bit-for-bit |
| Bit reads one bit at a time | — | Whole-word reads when all bits are present; short reads use the original loop | Identical values and errors |
| AAC decode and resample on the same thread | — | Decode thread with a bounded queue of 32 chunks (concurrent mode only) | Chunks delivered unchanged and in order |

**Not done, on purpose:** stereo downmix vectorization (it never showed up in the profile), hand-written AVX2, or a smaller IMDCT. Each of those changes floating-point results and would break byte-identity.

**Decode-thread failure handling (unit tests):**
- An error or panic in the source is reported.

- Pipeline cancellation is observed.
- Every test has a 10 s deadlock timeout.

## 4. Remaining limits

- **Not yet run on the EPYC host.** Re-run the benchmark there. With audio no longer the bottleneck, `--video-workers 3` or `4` may now beat N2, so re-test the worker count before changing any defaults.
- **Largest remaining audio cost** is the IMDCT's 8192-point f64 FFT, roughly two-thirds of the remaining AAC decode time in the profile. A standard 512-point IMDCT would be much faster but changes float results slightly. That needs a tolerance rule you approve (for example max |Δsample| and Mel MAE limits), not a byte-identity gate.
- **Toolchain.** Built with Rust 1.95.0; the pinned 1.98.1 couldn't be downloaded here. `bin/tenzor-v0.2.0-linux-x86_64` is that 1.95 build. Rebuild with the pinned toolchain for release.
- **Not repeated this cycle:** `cargo deny`, the 22-minute memory run, the LD_PRELOAD disk-write audit and the PyTorch loader tests. Output bytes are identical, so loader behaviour is unchanged, but those gates were not re-executed.
- **Evidence folder:** the existing Python suites refreshed some top-level `evidence/` files during this run.
